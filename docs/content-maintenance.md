# 掲載情報の更新手順

1. 運営元の公式告知、製品公式のセキュリティ案内、公式動作要件を読む。
2. その資料がどのサービス・問題・日付を対象にしているかを確認する。
3. PHP利用の説明と、その脆弱性への対応を別々に記録する。情報流出は事案を分け、流出の確認状況と事業者の対策状況を別々に記録する。
4. 利用者の具体的な作業指示がなければ、未確認と記録する。
5. 公式の説明と、アプリ側の一般的な確認手順を混ぜない。
6. 出典URL・公開日・確認日を記録する。公開日が確認できなければnullにする。
7. 新しいドメインを登録する場合は、そのドメインが資料の対象サービスに属する根拠を確認する。
8. `roles` と立場ごとの `groupByRole` を設定する。閲覧・買い物のサービスは利用者向け、CMS・レンタルサーバーは管理者向けを基本とし、ショップ運営など両方に必要な項目だけ共通にする。
9. `keywords` に一般的な呼び方を登録し、名前検索と用途の組み合わせを確認する。
10. `npm run build`、`npm test` とブラウザ操作で確認する。

出典の `kind` は `technical` (技術要件など)、`incident` (対象問題の説明)、`support` (問い合わせ・お知らせ窓口)、`domain` (ドメインの確認) を区別します。サポート窓口は `supportSourceIds` に登録し、PHPの利用や修正済みの根拠として流用しません。ドメインの根拠は `domainSourceIds` に記録します。

対象問題を確認できる公式資料が未掲載でも、確認窓口を登録して案内できます。その場合は `php` を「未確認」、`incident` を「掲載情報なし」とし、空の根拠配列を保ちます。検索で見つからないことを、公式発表が存在しない根拠にはしません。

「復旧」「メンテナンス完了」だけでは、特定の脆弱性の修正や被害の有無を推定しません。PHP更新の告知だけから、後日公表された問題まで修正済みとはしません。

対象のPHP問題の根拠: https://www.php.net/archive/2026.php

- 2026-10-21: CVE-2026-109618 / CVE-2026-109619
- 2026-10-23: CVE-2026-115560に関する追加案内

各サービスの根拠URLは `src/catalog.mjs` と `src/catalog-retail.mjs`、`src/catalog-social.mjs`、`src/catalog-admin.mjs` にあります。


## 確認日と変更日の違い

- `sources[id].checkedAt`: その公式資料の本文を最後に確認できた日。単に検索した日や取得に失敗した日ではありません。
- 画面のサービス別の情報確認日: 参照資料の確認日のうち最も古い日。一部の資料だけ読み直しても、全情報が新しいと見せません。資料ごとの日付は出典一覧で確認できます。
- `src/updates.mjs` の `type: 'content'` の日付: このガイドで説明や根拠を変更した日。事業者が修正を適用した日とは異なります。
- `trackedSince`: 変更履歴の記録開始日。初期値は2026-10-24。これ以前の変更日は記録がないため表示しません。
- `appReleases`: アプリの機能・表示の更新。サービスの対応状況と混同しません。

記録開始時の履歴はbaselineです。変更記録のない欄や「掲載情報なし」は、公式発表の有無や安全性を判定するものではありません。

自動差分確認は `scripts/catalog-snapshot.mjs` を使用します。調査前後のスナップショットを比較し、`changes`・`incidentChanges`・`reviewChanges` と、確認日だけの `verificationChanges`・`reviewVerificationChanges` を分けてレビューしてください。日次運用のコマンドと履歴の追加形式は `docs/automatic-updates.md` に記載しています。


## 情報流出の事案を追加・更新する

`src/incidents.mjs` の `breachIncidents` と `breachSources` を更新します。`breachReviews` には調査を試みた範囲と日付を残します。公開されている公式の告知だけを根拠とし、流出データそのものや個人情報は収集・保存しません。

- `id` は事案ごとに固定し、続報で変えません。同一サービスで別の出来事が発生したら新しい事案にします。
- `serviceIds` は告知で確認できる掲載サービスにのみ紐付けます。子サービス・機能・サーバー・対象者が限定される場合は、`title` と `scope` にその範囲を明示します。
- `publishedAt` は公表日、`updatedAt` は公式の更新日です。わからない日付をガイドの確認日で埋めません。`occurredAt` と `affectedPeriod` は公式説明から確認できた発生・対象期間です。
- `dataTypes` と `excludedData` は、流出・露出した情報、可能性がある情報、対象外と公表された情報の区別を保って記述します。対象者全員について同じ情報が流出したとは推測しません。
- `status` は流出についてわかったこと、`providerResponse` は事業者が行った調査・対策、`officialAction` は公式に案内された利用者の手続きです。これらを一つの「対応済み」で置き換えません。
- `sourceIds` はPHP用の出典と重複しないIDを使用します。公式本文を読めた日だけ、対応する `breachSources[id].checkedAt` を更新します。
- `history` はこのガイドでその事案の内容を変更した記録です。初回掲載は過去の事件発生日と区別し、再確認だけでは新しい内容変更を追加しません。
- `breachReviews[serviceId].attemptedAt` は調査を試みた日です。検索で該当資料を見つけられなくても「被害なし」とは表示しません。取得失敗を、以前の有効な説明の削除や確認日の更新に使いません。

過去の公表を追加する場合は、古い事案であることを見出し・説明に記します。最新の続報がある場合は元の公表と合わせて読み、変更内容を確認します。公式の被害公表と、一般的な注意喚起や疑わしいメールへの警告も区別してください。

更新後は事案の表示、利用状況による確認事項、メモ出力、更新履歴を検証します。日次タスクはGitHubへのpush後に有効となる設定で、サイト公開を待たずに調査・レビュー用Pull Requestまでを行います。自動マージとデプロイは行いません。
