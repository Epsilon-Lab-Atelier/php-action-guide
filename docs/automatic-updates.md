# 公式情報の定期調査と差分更新

## 構成

GitHub Pagesは静的ファイルを配信します。公式情報の調査はアプリの外側で動く定期実行タスクが担当し、変更案をGitHubの作業ブランチとPull Requestにまとめます。アプリ本体から検索APIやAIへ接続することはありません。

定期実行の予定は日本時間の毎朝8時ごろです。実行予定と成否は定期実行タスク側で管理します。このリポジトリにファイルを置くだけでは、定期実行タスク自体は作成されません。

## GitHubへの反映後の開始条件

対象は `Epsilon-Lab-Atelier/php-action-guide` です。`maintenance/policy.json` の `activation` は `repository_push` で、サイト公開を開始条件にしません。

1. 認証アカウントが `Epsilon-Lab-Atelier` と一致することを確認する。
2. 対象リポジトリの既定ブランチで、このアプリのソースと `maintenance/policy.json` を読む。
3. `repository` と `account` が上記の対象に一致し、`repositoryConfirmed=true`、`enabled=true`、`activation="repository_push"` であることを確認する。
4. 同じリポジトリに向けた定期実行タスクを使う。空のリポジトリや未反映の設定では開始せず、別のリポジトリへ切り替えない。

この設定が既定ブランチへpushされた後、毎朝の調査対象にPHPの問題と情報流出を含めます。`publishedSiteUrl` がnullでも調査とレビュー用Pull Requestの作成は可能です。サイトの公開・デプロイは別途行い、このタスクからは実行しません。停止時は `enabled` を `false` にするか、定期実行タスクを停止します。

## 1回の調査

1. 認証アカウントが `Epsilon-Lab-Atelier` であることを確認する。別のアカウントへ切り替えない。
2. 既定ブランチの最新版と既存の更新用Pull Requestを読み、開始条件を確認する。
3. PHP公式の対象問題・追加案内と、掲載中の全サービスの公式告知・ヘルプ・セキュリティ案内を調べる。PHPへの対応と、最近の情報流出・不正アクセスの公表を別々に調査する。既存URLの変更検出だけで終えず、新しい公式告知や続報も探す。根拠未掲載の項目を優先する。
4. 公式ページの本文を読み、サービス・問題・影響条件・説明時点・利用者への指示を確認する。検索結果の見出しだけで断定しない。
5. PHPの利用、対象問題への対応、利用者の手続きを分けて記録する。情報流出は `src/incidents.mjs` に事案ごとに記録し、流出の確認状況、事業者の対策、利用者の手続きを分ける。公式窓口へのリンクだけでは、PHP使用・修正済み・流出なしの根拠にしない。
6. 調査前後のカタログをスナップショットにし、下記の差分コマンドで確認する。意味のある変更が確認できた場合は、対象のカタログ・出典、事案の `history` と `src/updates.mjs` の変更履歴を更新する。確認日だけの変更は本文の変更と分ける。`npm run build` と `npm test` を実行し、生成HTMLも更新する。
7. 匿名性、差分、出典、検証結果を確認し、更新用ブランチ `maintenance/official-information` のPull Requestを作成または更新する。既存の未反映案と重複させず、無関係な変更は含めない。

## 情報流出の調査範囲と記録

- `src/incidents.mjs` の `breachIncidents` は、公式発表を本文まで確認した事案です。一つのサービスに複数の事案を紐付け、`id` で区別します。既存のPHP問題と原因が同じとは推定しません。
- 対象となるサービス・サブサービス・機能・契約者・利用期間を公式本文から確認します。同じ企業の別サービス、出店店舗、外部委託先の事故を親サービス全体へ広げません。影響する範囲が限定されている場合は、カードの見出しと `scope` に明示します。
- 公表日、公式の更新日、発生・対象期間、対象情報と対象外の情報、未確認点、公式の対応案内、根拠を分けて記録します。対象情報を断定できなければ推測で埋めません。
- 「流出を確認」「可能性あり」「調査中」などは公式本文の範囲で使います。「対策実施」「復旧」「調査完了」を、過去の流出がなかったことや利用者の対応不要へ読み替えません。
- 昔の事案にも現在の利用者が参照する価値がある場合は掲載できます。ただし公表年と対象期間を明記し、最近起きた事件や新しい被害として紹介しません。既存の古い告知を再発見しただけで新規事件として通知しません。
- `breachReviews` はサービスごとの調査範囲と試行日を記録します。検索した日を `attemptedAt`、公式資料を実際に読めた日を `breachSources[id].checkedAt` とし、混同しません。検索で見つからなかった場合は「調査範囲で掲載できる公式公表を確認できず」とし、「事故なし」「安全」とは記録しません。
- 登録・購入・投稿などの利用方法や、退会済み・配送先登録などの選択は確認事項を絞るために使います。選択のみで個人の被害を判定したり、個人情報を入力して外部照会したりする機能は追加しません。

## 日付・取得失敗・変更なし

- 公式ページを実際に読めた日を、出典の確認日として記録する。検索を試しただけの日や、取得に失敗した日で確認日を上書きしない。
- カタログ全体の確認日を更新するには、対象説明と掲載情報全体を再確認する。一部だけ確認できたときは、その出典の確認日だけを更新する。
- 取得失敗は対応状況の変化ではない。既存の根拠や説明を消さず、失敗した確認先を調査結果に残す。
- 内容に変更がなくても、本文を実際に再確認できた出典の確認日は記録できる。確認日だけの差分は「再確認」として区別し、内容変更日や新しい対応指示として表示しない。不要な通知を避け、既存の更新用Pull Requestにまとめるか定期実行タスク側に記録する。公開版へ反映されるまで画面の確認日は更新されない。
- 判断が分かれる内容は未確認のままにし、候補資料と判断できない点を更新案に記載する。
- 新たな利用者の対応指示、重要な変更、更新を妨げる取得・認証・検証の失敗は通知する。成功したように報告しない。

## 更新権限の範囲

自動更新は、調査・ファイル差分・レビュー用Pull Requestまでです。自動マージ、公開設定の変更、デプロイ、他のリポジトリへの書き込みは行いません。公開への反映は、別途依頼された公開手順に従います。

コミットの表示名には `Epsilon-Lab-Atelier`、メールには同アカウントのGitHub noreplyアドレスを使用します。本文・出典の要約・ログ・画像・履歴に、開発者個人を特定する情報や認証情報を含めません。

## 利用者向け案内の改善方針

技術情報が未確認でも、利用者が次に何を確認すればよいかは説明できます。「未確認」を繰り返す前に、公式のお知らせやアプリ内通知に自分向けの手続きがあるかを確認するよう案内します。サービス側のPHP更新と、一般利用者に求められる作業を区別します。

掲載項目は、対象問題の公式説明を掲載できた段階、関連告知との関係が未確認の段階、公式窓口を案内する段階を区別します。未掲載の資料を調べ、「公式発表がない」と「このガイドにまだ掲載していない」を混同しません。


## 実行できる差分確認

`maintenance/catalog-baseline.json` は、2026-10-24に既存の掲載内容から作成した記録開始時点の写しです。今回新しく公式調査をしたという意味ではありません。記録開始の基準として残し、日次調査では毎回、調査開始直前の既定ブランチから作業用の写しを作ります。

```sh
node scripts/catalog-snapshot.mjs write /tmp/service-catalog-before.json
# 公式の本文を確認し、必要なカタログ修正を行う。
node scripts/catalog-snapshot.mjs write /tmp/service-catalog-after.json
node scripts/catalog-snapshot.mjs diff /tmp/service-catalog-before.json /tmp/service-catalog-after.json
```

差分結果は次の区分で読みます。

| 出力 | 内容 |
| --- | --- |
| `changes` | 従来のサービス・PHP説明の内容変更 |
| `incidentChanges` | 情報流出の事案ごとの追加・変更・削除。`incidentId`、関連する `serviceIds`、変更 `fields`、根拠 `sourceIds` を含む |
| `reviewChanges` | サービスごとの調査範囲・結果説明の変更。新たな流出の確認とは限らない |
| `changedSourceIds` | 根拠本文・URL・公表日等の変更 |
| `verificationChanges` | PHP・情報流出の出典確認日の差分 |
| `reviewVerificationChanges` | 情報流出の検索・確認試行日 `attemptedAt` の差分 |

確認日・試行日だけが進んでも `hasContentChanges` はtrueになりません。`hasContentChanges` がfalseでも「安全」とは判断しません。参照する根拠URLや公表日を変えた場合は、その資料を使うサービス・事案の変更として扱います。キーの並び順だけでは内容変更になりません。

スナップショットはPHPと情報流出の出典を共通の `sources` に統合します。出典IDの衝突はエラーです。`incidents` と `breachReviews` のない旧schemaVersion 1の基準データも読み込めます。保存済みの初期baselineは上書きしません。

確認試行を機械的に点検するには、JSON配列の試行記録を用います。

```json
[
  {
    "sourceId": "noteNotice",
    "attemptedAt": "2026-10-24",
    "outcome": "unconfirmed",
    "bodyRead": false
  }
]
```

これは形式の例です。実際の本文を読めた場合にだけ `outcome` を `read`、`bodyRead` をtrueにし、登録済み資料と一致する `url` を指定します。日付は実際に確認した日です。

```sh
node scripts/catalog-snapshot.mjs review /tmp/service-catalog-before.json /tmp/service-source-reviews.json /tmp/service-review-result.json
```

出力は確認日を反映した `snapshot`、採用したsource IDの `accepted`、取得失敗・未確認等の `deferred` です。既存資料を消さず、失敗した試行で確認日を進めず、一部の再確認でカタログ全体の日付を進めません。異なるURL、存在しないsource ID、重複試行、確認日の後退はエラーになります。このコマンドは資料を読んだかどうかを自動判定するものではなく、調査担当が確認した記録を検査する補助です。出力はレビュー用で、カタログ本体を書き換えません。

## 掲載内容の履歴を残す

`src/updates.mjs` の `updateHistory` に、確認できた内容変更だけを `type: 'content'` として追加します。必要なフィールドは `id`、`type`、`date`、`serviceIds`、`sourceIds`、`title`、`summary` です。短い日本語で、何が新たにわかったかと、利用者が読み直す点を記述します。日付はこのガイドの内容を変更した日で、サービスの修正日ではありません。確認日の更新だけではcontentイベントを追加しません。

情報流出の変更は該当事案の `history` にも、掲載内容を変更した日と説明を残します。日次の通知では公式の公表日・対象期間と、このガイドへの反映日を区別してください。

初期の `baseline` イベントは記録開始の説明です。過去の更新日時は推測で補いません。UI機能やデザインの更新は `appReleases` に記録し、公式対応情報の更新と分離します。公開前の履歴・確認日も、実際に検証できた内容の範囲だけを表します。
